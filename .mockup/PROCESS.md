# `.mockup/` 原型管理规范（PROCESS）

> 目的：解决「原型与真实 UI 脱节」「review 指南滞后」「实现状态不可跟踪」三个问题。
> 采纳于 2026-08-04（用户反馈 env-launch-entry 初版与真实布局差异大之后）。

## 原则

1. **原型 = 真实代码的结构镜像**，不是独立设计稿。新建原型前先读对应真实组件（`frontend/app/...` / `pkg/...`），逐字段对齐 DOM 结构与文案；仅在真实组件上加「新增点」。
2. **每个原型目录必须有 `README.md`**，顶部带统一状态标记（见下）。
3. **目录即状态容器**：`_to-keep/`（活跃设计）、`_to-delete/`（已落地/被取代）、`_review-boundary/`（待拍板）；新增原型进 `_to-keep/` 或自建目录。

## 状态标记（README 顶部，统一格式）

每篇原型 README 第一段 blockquote 必须包含三行：

```markdown
> 同步状态：▲ 设计活跃（未实现）｜● 已落地（真实组件已实现）｜▼ 过时待清理｜◐ 部分落地
> 镜像源：frontend/app/workspace/widgets.tsx（真实组件路径，可多个，逗号分隔）
> 最后同步：2026-08-04（最近一次对齐真实代码的日期）
```

- 新增原型：写 `▲` + 镜像源 + 当天日期。
- 真实组件实现后：改为 `●`，仍保留镜像源（用于追溯）。
- 镜像源已不存在或组件被重构取代：改 `▼`，移到 `_to-delete/`。

## 集中索引与对账

- `__REVIEW_GUIDE__.md` 是唯一索引总表：**分类 + 每项一句话 + 状态**。新增/移动原型时同步更新。
- 对账脚本 `node docs/sync-audit/audit-sync.mjs`（已移入 `docs/sync-audit/`，`--json` 供审批）：
  - 扫描所有 README.md，解析「同步状态 / 镜像源 / 最后同步」三行；
  - 校验每个镜像源在真实代码仓库里是否仍然存在；
  - 输出报告：原型｜状态｜镜像源存在与否｜最后同步距今｜建议动作。
- 跑对账的时机：**任何 UI 组件重构后**、**新增原型时**、**每月一次**。

## 生命周期

```
新建（写 README + 状态 ▲ + 镜像源）
   ↓ 评审通过
设计定稿 → 进入落地（状态 ◐）
   ↓ 真实组件实现完成
已落地（状态 ●，保留镜像源）
   ↓ 组件重构/原型被取代
过时（状态 ▼ → 移 _to-delete/，留待批量清理）
```

## 检查清单（新建/更新原型时）

- [ ] 镜像源路径填写真实，且路径存在
- [ ] DOM 结构、类名、文案逐字段对齐真实组件
- [ ] 只新增「设计新增点」，不虚构整个弹窗
- [ ] README 顶部三行状态标记齐全
- [ ] `__REVIEW_GUIDE__.md` 总表已更新
- [ ] 跑一次 `node docs/sync-audit/audit-sync.mjs`，无「镜像缺失」告警

## 与 Obsidian 方案笔记的关系

- 原型 README 首行应引用对应 Obsidian 方案笔记（wikilink 或路径），便于设计→实现的追踪。
- Obsidian 方案笔记在「原型落地计划」一节记录 `.mockup/` 目标目录（如 env-launch-entry 已如此）。
