Common Text 重构设计

需求理解 → 设计方案 → 交互示意 → 数据流 → 实施路线图

1. 需求理解

用户的核心诉求有三点：

  1. 文本编辑友好度 — 当前 terminal 里用 agent 做文本编辑不友好（换行、多行、光标定位、选择复制都很痛苦），需要一个类似 AI Web 端的文本编辑框。
  2. Common Text 快速关联 — 在编辑框输入时，能快速搜索、引用已保存的 Common Text，类似 @ 提及或 / 命令触发器。
  3. 选中内容 → Common Text — 编辑框内选中文本后，能一键将其保存为新的 Common Text 条目。

3. 新组件设计：CommonTextEditor
3.1 组件定位

CommonTextEditor 是一个独立的多行文本编辑组件，放置在 terminal block 内部或作为侧边面板。 它有两种使用形态：内嵌模式（在 terminal 底部或侧边作为输入区）和独立面板模式（如 AI Panel 的输入框）。

5. 架构设计
5.1 组件结构
CommonTextEditor
─── 主编辑器容器
├── Toolbar — 发送、插入 CT、保存选中 CT、格式辅助按钮
├── InsertCommand — 点击触发 @mention 下拉
└── MentionDropdown — 搜索列表 + 键盘导航 + 标签过滤
├── EditableArea — contentEditable div 或 textarea
└── 支持 @mention 内嵌显示（可选）、多行编辑、光标控制
├── SelectionBar — 选中文本时出现浮动/固定条
└── "保存为 Common Text" / "插入 Common Text" / "复制"
└── TagChips — 底部已选标签展示
5.2 两种使用形态
形态 A：内嵌模式
放置在 Terminal block 内部底部区域，作为 terminal 的"输入增强层"。

特点：
  • 占用 block 内底部 ~120px 高度
  • 可折叠/展开
  • 发送内容到 terminal（ControllerInputCommand）
  • 动态在 terminal 和 editor 之间切换（@ 触发 / Tab 键）
形态 B：独立面板模式
作为独立 view type（view: "commontexteditor"）或侧边面板存在于 terminal 旁边。

特点：
  • 类似 AI Panel，可打开/关闭
  • 可拖拽调整宽度
  • 同时关联 terminal 上下文（当前 cwd、connection）
  • 支持 @mention + 标签管理 + 一键发送
5.3 数据流
用户输入 @
└─ Editor 监听 input/composition 事件
├─ 检测到 @ 后，获取光标位置
├─ 调用 searchCommonTextItemsPaged()
├─ 在光标坐标处渲染 MentionDropdown
├─ 键盘导航（↑↓ Enter Esc）
└─ 确认 → 插入文本/拆分为 MentionBlock
用户选中文本 → 保存
└─ 监听 selectionchange 事件
├─ 有选中文本时，显示 SelectionBar
├─ 点击"保存" → upsertCommonTextItem()
├─ 自动提取标题（首行/截断）、标签（可选输入）
└─ Toast 提示"已保存"
发送内容到 Terminal
└─ 点击发送 / Cmd+Enter
├─ 提取纯文本（排除 @mention markup）
├─ 调用 TermViewModel.sendDataToController()
└─ 清空编辑器（或保留，取决于配置）
5.4 编辑器渲染策略

这里有两种编辑器实现路径，各有优劣。建议做技术论证后选择。

方案 A：contentEditable div
✅ 原生支持富文本（@mention 内嵌显示、选中高亮）
✅ 光标控制精确（selection API）
✅ 可嵌入真实的 Mention chip
❌ contentEditable notoriously 不稳定
❌ 需要处理富文本 → 纯文本序列化
❌ 浏览器差异大

适用场景：需要 @mention 内嵌显示和富文本编辑
方案 B：Textarea + 浮层 @提及
✅ textarea 原生可靠，跨浏览器一致
✅ 光标定位、选区操作简单
✅ 性能好，大文本无压力
❌ 富文本能力有限（仅高亮/遮罩）
❌ @mention 以浮层形式显示，不在文本流内
❌ 选中文本高亮需要额外处理

适用场景：稳定优先，@mention 通过浮层触发

推荐方案 A（contentEditable + Mention chips），理由： AI Web 端输入框的用户体验预期是 @mention 内嵌显示（如 Slack、Notion）， contentEditable 虽然复杂但本项目已有 textarea/modal 经验，且 mention 内嵌是核心差异化体验。 通过 Slate.js 或 ProseMirror 等编辑器框架可以大幅降低 contentEditable 的复杂度。

6.2 提及的内部表示

@mention 在编辑器中以 MentionBlock（不可编辑的原子节点）存在。 内部定义为 mentionBlockId 属性，序列化时展开为实际文本内容。

MentionBlock 的 data-id 存储 Common Text Item 的 id， data-text 存储实际文本（用于粘贴/复制时展开）。

7. 选中文本 → Common Text 流程
步骤 1：选中
用户在编辑框内用鼠标/双键/Shift+方向键选中一段文本。
系统监听 selectionchange 事件，检测是否有有效选区。
步骤 2：浮出选区条
选区出现后，在选区上方或编辑器固定位置显示操作条：
"保存为 Common Text" / "插入" / "复制"
也可通过按钮（➕）或快捷键（⌘S / Ctrl+S）
步骤 3：保存
调用 upsertCommonTextItem({title:"", text: selectedText})
自动生成标题（首行截断 / "Untitled" fallback）
可输入标签，也可事后在 Common Text Manager 中编辑
Toast 提示 + 可选即时在侧边面板中更新

9. 与现有系统集成
9.1 复用现有模块

设计尽量复用已有的 Common Text 基础设施，不重新造轮子：

  • 搜索逻辑：重用 searchCommonTextItemsPaged()（后端分页搜索）、getCommonTextTagSummaries()
  • CRUD 逻辑：重用 upsertCommonTextItem()、addSelectionToCommonText()、saveCommonTextItems()
  • 事件系统：扩展 CommonTextSearchDetail 增加 insertTarget?: HTMLElement，让 editor 可被指定为插入目标
  • 标签组件：复用 CommonTextTagChip、CommonTextTagList
  • 搜索弹窗：可复用 CommonTextSearchModal（通过 📋 按钮触发完整搜索）
9.2 TermViewModel 集成

在 TermViewModel 中新增 CommonTextEditor 相关的 atoms 和方法：

  • editorVisibleAtom — 编辑器可见性
  • editorContentAtom — 编辑器当前文本
  • editorMentionStateAtom — 提及下拉状态（open, query, selectedIndex...）
  • sendToTerminal(content) — 将编辑器内容发送到 terminal
  • openCommonTextInsert() — 在编辑器中打开提及搜索

14. 设计要点总结
核心设计决策
1. 复用优先：最大化复用现有 Common Text 模型/搜索/CRUD
2. contentEditable：用 contentEditable 实现富文本 mention，Phase 1 可先做纯文本
3. @ 触发：输入 @ 弹出搜索下拉，AI Web 端用户最熟悉的交互模式
4. 选中保存：selectionchange → SelectionBar → upsertCommonTextItem
5. 内嵌模式：editor 在 terminal 内部，Tab 切换，无缝衔接
6. 扩展事件：新增 insertTarget 和 onConfirm 回调，让 editor 可被任何组件触发
待讨论/确认
1. contentEditable vs textarea：是否引入 Slate/ProseMirror，或先做 textarea 方案？
2. editor 放在哪里：terminal 内部底部 / 独立侧边面板 / workspace 底部栏？
3. mention 显示方式：内嵌 MentionBlock vs 浮层预览 vs 纯文本标记？
4. 发送后行为：清空编辑器 / 保留内容 / 可配置？
5. 与 AI Panel 的关系：CommonTextEditor 是否替代/合并 AI输入框的某些能力？
6. 标签输入：保存选中文本时，标签是手动输入还是自动从上下文推断？
