# 会话详情滚动卡顿：CDP 实测报告与修复

日期：2026-10-27
关联任务：`10-27-aisessions-scroll-perf`（父任务 `10-19-aisessions-ux-perf-overhaul`）
状态：已实现并验证；剩余部分见「未做完 / 下一步」。

## 1. 问题

大会话详情滚动时不顺畅（不是加载，是**滚动过程**）。用户体感「一顿一顿」，快速甩动时更明显。

## 2. 测量方法（可复现）

用 CDP 直接打真实运行中的 Electron 渲染进程，不靠猜：

1. `http://127.0.0.1:9222/json/list` 拿 page target，连 WebSocket。
2. **必须先解除后台节流**，否则测不到真实帧：
   - `Emulation.setFocusEmulationEnabled { enabled: true }`
   - `Page.setWebLifecycleState { state: "active" }`
   - `Emulation.setIdleOverride { isUserActive: true, isScreenUnlocked: true }`
   - 验证 `document.visibilityState === "visible"`、`document.hidden === false`
   - 不做这一步时 `setTimeout(100)` 实测要 ~660ms，rAF 直接不跑，探针会挂到超时。
3. 滚动容器定位：从 `[data-testid=aisessions-virtual-timeline]` 向上找第一个
   `overflow-y` 为 `auto|scroll` 的祖先（注意中间还套了一层无 class 的 div，
   `parentElement` 不是滚动容器）。
4. 逐帧 `scrollTop -= delta` + `await requestAnimationFrame`，统计帧间隔
   p50 / p90 / max，并用 `PerformanceObserver({ entryTypes: ["longtask"] })` 统计长任务。
5. 用 `Performance.enable` + `Performance.getMetrics` 取
   `TaskDuration / ScriptDuration / LayoutDuration / RecalcStyleDuration / LayoutCount` 的增量。
6. 用 `Profiler.start` / `Profiler.stop` 取 CPU profile，按 `node.hitCount` 聚合自耗时。

## 3. 实测结果（优化前）

同一会话（内容高约 18.5k px，可见行 11~28），每帧下滚 260px × 60 帧：

| 指标 | 数值 |
|---|---|
| TaskDuration | 2391.7 ms |
| ScriptDuration | 1611 ms |
| LayoutDuration | 357 ms |
| RecalcStyleDuration | 236 ms |
| LayoutCount | 107 |
| RecalcStyleCount | 169 |
| 帧间隔 p50 / p90 / max | 32~42 / 49~98 / 108~235 ms |

CPU profile 自耗时 Top：

| 占比 | 函数 |
|---|---|
| 22.6% | `measureElement`（`session-detail.tsx`，`element.offsetHeight` 强制同步布局） |
| 21.7% | `exports.jsxDEV`（React dev 元素创建，主要是新挂载行） |
| 9.5% | `(program)` 浏览器原生 |
| 8.7% | `measure`（`session-message.tsx`，Ticker 的 `offsetWidth`） |
| 4.6% | `(anonymous) native` |
| 3.6% | `jsxDEVImpl` |
| 1.4% | `anchorHash`（`annotation-model.ts`，本不该在滚动时跑） |

慢速（每帧 60px）profile 里 `jsxDEV` 占 23.6%、`measureElement` 占 18%、`anchorHash` 占 1%。

## 4. 根因

### 根因 1（最要命）：`liveTimelineItems` 每帧新建 `[]`，打穿整条 memo 链

```tsx
// 旧
const liveTimelineItems = liveTurn != null ? liveTurnToTimelineItems(...) : [];
```

无 live turn 时每次都返回**新数组**，于是下游全部失效、每帧重算：

- `renderItems`（useMemo 依赖它）
- `rows`（`groupConsecutiveTools`）
- `seqToIndex` / `anchorKeyToSeq`
- `timelineAnnotationAnchors` → **对全部消息重算 `anchorHash`**
- `timelineAnnotationAnchorSignature`（全量字符串拼接）
- `timelineItemSeqs`

大会话 = 每帧几千次哈希 + 多个数组重建。这也是 profile 里 `anchorHash` 出现在滚动热点的原因。

### 根因 2：`measureElement` 的强制同步布局没有作用域

`measureElement: (el) => el.offsetHeight` 每次读都强制同步布局。滚动时一次 DOM 批量插入后，
多个 `offsetHeight` 读取会反复触发整块滚动容器（近 8k 节点）重排 = layout thrash。

**A/B 实验**（同一页面、同一内容、紧邻两轮，最可信的一组数据）：

| 方案 | p50 | p90 | max |
|---|---|---|---|
| 基线 | 41.9 | 97.6 | 235.3 |
| 行容器 `contain: layout style` | **22.9** | **44.9** | **98.9** |
| 行容器 `contain: layout style paint` | 28.3 | 44.8 | 121.4 |
| `content-visibility: auto` + intrinsic-size | 61.0 | 103.2 | 166.3（更差，弃用） |
| `will-change: transform` + `backface-visibility` | 44.5 | 114.8 | 528.7（更差，弃用） |

### 根因 3：滚动时整块父组件重渲染，可见行元素树每帧重建

virtualizer 范围一变就重渲染整个 `SessionDetailPane`（近 2200 行），旧写法在 `map` 里直接调
`renderTimelineItem(...)`，等于每帧为所有可见行重建一次元素树（`jsxDEV` 20%+）。
（注：行内容本身没有被 mutate，`MutationObserver` 实测 0 次变更，所以不是 markdown 重解析。）

## 5. 已做的修复

1. **稳定空时间线数组**（`session-detail.tsx`）
   ```tsx
   const EmptyTimelineItems: SessionDetailTimelineItem[] = [];
   const liveTimelineItems = useMemo(
       () => (liveTurn != null ? liveTurnToTimelineItems(liveTurn, liveUserMessagePersisted) : EmptyTimelineItems),
       [liveTurn, liveUserMessagePersisted]
   );
   ```
   修完后一次干净对比：ScriptDuration 1611 → 1102ms（-32%）。

2. **行容器 `contain: layout style`**（`session-detail.tsx` 虚拟行 style）
   让 `measureElement` 的强制布局只影响该行，而不是整个滚动容器。

3. **`TimelineRow` memo 包装**（`session-detail.tsx`）
   行级 memo：纯滚动时 `item / index / items / render` 引用稳定 → 跳过元素重建；
   只有真正影响渲染的依赖（搜索词、展开工具、批注数、子代理匹配）变化时
   `renderTimelineItem` 换引用，行才重渲。

已有修复（本次之前的提交 `78fb3c5a`）：`translateY` 取整像素、滚动容器 `overflow-anchor: none`、
虚拟行禁播 `ly-enter`、按行类型估高。

## 7. 未做完 / 下一步

**重要前提：以上数据全部来自 dev 构建**（`127.0.0.1:51742`，Vite dev + React dev）。
profile 里 `jsxDEV`、`validatePropertiesInDevelopment`、`runWithFiberInDEV`
都是 dev-only 开销，生产构建下会显著下降。**建议先用打包版复测**，再决定是否继续投入。

如果产物版仍不顺畅，按 ROI 排序的下一步：

1. **把虚拟时间线拆成独立子组件**：让 virtualizer 的范围变化只重渲染时间线，
   不再牵动 pane 的头部 / 大纲轨 / 批注轨 / composer（这是目前唯一还在放大的结构性成本）。
2. **`AnnotationRail` 加 memo + 稳定回调**：现在是普通函数组件，且 props 里有内联箭头闭包。
3. **降级 `measureElement` 策略**：改用 `requestAnimationFrame` 批量测量，避免与滚动写入交错
   （需谨慎，会影响跳动）。
4. **考虑 `WaveStreamdown` 的挂载成本**：新行进视口才解析 markdown，属必要成本；
   若要进一步压，只能做「先纯文本占位、空闲再解析」，风险较高，暂不建议。
