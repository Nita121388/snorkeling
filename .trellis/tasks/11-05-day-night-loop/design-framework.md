Lead: 三段真实的 /loop 指令暴露了循环真正难的地方：不是跑得快。难在每条输入都有归宿、每次合并都实测过、每个 agent 都会长记性。

## A 三段真实 /loop 说了什么 {span=2}

| 来源 | 原话要点 | 抽出的机制 |
|---|---|---|
| 一 · GitHub 三面盯守 | 盯 issues、盯 PR、盯 Discord 全部 channel。修完要发版并回复，不值得也要回复。PR 要拉下来实际跑，确认没 bug 才合并 | 多源入口 · 必有归宿 · 合并前实测 · 覆盖率硬要求 · 通知要真触达 |
| 二 · 技术债与经验 | 定时清理屎山与恶意代码。把"哪些不该合并、哪些验证不缜密"写进经验，防止以后 agent 犯同样错误 | 周期性防腐 · 教训沉淀 |
| 三 · Twitter 与成本 | 先让便宜的决策模型判断推文是否相关。不相关就忽略、不转发，避免浪费 Token | 成本闸门 · 廉价前置过滤 |

## B 三段里最值钱的一句 {span=2}

```callout
"我自己都没测过的 PR，你不能只看 diff 就合。" 三段指令都指向同一件事：判定必须可重复执行。这就是本项目的核心原则——验证能力先于开发。
```

## D 框架全景 {span=2}

```flow
(白天 原型与需求) -> 夜间队列: 入队且门清零
夜间队列 -> {人工门已清零?}
{人工门已清零?} --> 停泊横幅: 否
{人工门已清零?} -> 逐包执行: 是
逐包执行 -> {判据全绿?}
{判据全绿?} -> 独立提交: 是
{判据全绿?} --> 停泊横幅: 否
独立提交 -> 发版闸门
发版闸门 -> 晨报
晨报 -> 晨会验收
晨会验收 --> 白天 原型与需求: 打回重签
```

## F 两个正交状态，推出看板六列 {span=2}

| 列 | 进入条件 |
|---|---|
| 未就绪 | gateState 不为 clear，按门分组 |
| 今晚队列 | 门已清零，且 runState 为 idle 或 queued |
| 执行中 | runState 为 running |
| 待验收 | runState 为 green 或 committed |
| 待发池 | runState 为 accepted |
| 停泊横幅 | runState 为 parked，不进列 |

gateState 由凭据与 hash 实时推导。runState 由事件流折叠重建。两者相乘得到列。所以新增一道门只改一个函数。

## G 验证优先的证据阶梯 {span=2}

| 级 | 证据 | 最低适用于 |
|---|---|---|
| L0 | 肉眼说好了 | 不接受 |
| L1 | 单测红绿 | 后端与契约 |
| L2 | 真机 harness 计数 | 新功能 |
| L3 | L2 加 stash 对照 | Bug 修复 |
| L4 | L3 加像素或几何测值 | 样式缺陷 |
| L5 | rubric 逐条签字 | 样式重设计 |

器具的定义是三件：判据、已知坏样本、校准记录。永远绿的测试等于零信息。
