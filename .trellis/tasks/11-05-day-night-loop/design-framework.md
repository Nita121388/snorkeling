Lead: 三段真实的 /loop 暴露了循环真正难的地方：不是跑得快。难在每条输入都有归宿、每次合并都实测过、每个 agent 都会长记性。

## A 三段真实 /loop 说了什么 {span=2}

| 来源 | 原话要点 | 抽出的机制 |
|---|---|---|
| 一 · 三面盯守 | 盯 issues、盯 PR、盯 Discord 全部 channel。修完要发版并回复，不值得也要回复。PR 要拉下来实际跑，确认没 bug 才合并 | 多源入口 · 必有归宿 · 合并前实测 · 覆盖率硬要求 · 回信义务 |
| 二 · 技术债与经验 | 定时清理屎山与恶意代码。把"哪些不该合并、哪些验证不缜密"写进经验，防止以后 agent 犯同样错误 | 周期性防腐 · 教训沉淀 · 重复即沉淀 |
| 三 · Twitter 与成本 | 先让便宜的决策模型判断推文是否相关。不相关就忽略、不转发，避免浪费 Token | 成本闸门 · 廉价前置过滤 |

## B 三段里最值钱的一句 {span=2}

```callout
"我自己都没测过的 PR，你不能只看 diff 就合。" 三段指令都指向同一件事：判定必须可重复执行。这是本项目的核心原则——验证能力先于开发。
```

## C 三段验收，缺一不可 {span=2}

| 路 | 对象 | 谁做 | 出口 |
|---|---|---|---|
| 一 · 包验收（对内） | 夜间跑完的包 | 晨会 30 分钟 | 通过 / 打回 / 批注，证据按 L0–L5 计级 |
| 二 · 四面巡检（对外） | GitHub issues、GitHub PR、社区 Discord、社媒 Twitter | 白天分诊，夜间执行 | 每条必须有归宿：修 / 回信 / 记录后忽略 |
| 三 · 防腐与长记性 | 技术债、恶意代码、重复犯的错 | 每周一次，独立成包 | 清理清单 + 教训入库 + 拒绝清单 |

三条路的共同点：**没有归宿的条目不许消失**。这正是三段 /loop 最不像口号、最像工程约束的一条。

## D 我自己的输入：三层摩擦 {span=2}

有一条想法时，用什么渠道取决于它有多熟。用重渠道记轻想法，那条想法就不会被记下来。

| 想法熟到哪一步 | 记在哪 | 摩擦 | 怎么进流程 |
|---|---|---|---|
| 一句话，还没想清 | loop/INBOX.md 一行 | 5 秒 | 分诊时变成包 / 任务 / 丢弃 |
| 想清了是个改动，判据能写 | queue.mjs add --origin self | 1 分钟 | 直接进队列，补 g2 红证 |
| 要设计、要先问需求 | task.py create | 5 分钟 | 走 G1 需求确认 |

INBOX 允许粗糙：不分类、不写判据、不写期望值。铁律只有一条——分诊必须三选一，没有第四条路。

分诊时机是晨会后 10 分钟，或睡前排队列时。绝不攒过三天。

## E 工作项长什么样：一篇笔记 {span=2}

| frontmatter | 取值 | 谁写 |
|---|---|---|
| id / title / type | 固定 ID、一句话标题、8 类之一 | 人 |
| priority | P0 / P1 / P2 / P3，**可手改**，改完即改开工顺序 | 人 |
| origin / source | 来源渠道与出处（INBOX #n、某个 issue、谁提的） | 人 |
| touch / budget | 路径白名单、预算 | 人 |

正文四个固定小节：背景（为什么）· 来源（谁提的）· 验收判据（命令 → 期望值）· 记录（结论与教训）。

机器只写 `gates.json` 里的凭据。人写字段与机器写字段分开存，各只有一个写者，所以不会漂移。

## G 框架全景 {span=2}

```flow
(我的 INBOX 与随手笔记) --> 白天分诊
(GitHub issues 与 PR) --> 白天分诊
(社区与社媒反馈) --> 白天分诊
(白天 原型与需求) -> 夜间队列
白天分诊 -> 夜间队列: 值得做
白天分诊 --> 回信清单: 只需回复
夜间队列 -> {人工门已清零?}
{人工门已清零?} --> 停泊横幅: 否
{人工门已清零?} -> 逐包执行: 是
逐包执行 -> {判据全绿?}
{判据全绿?} -> 独立提交: 是
{判据全绿?} --> 停泊横幅: 否
独立提交 -> 发版闸门
发版闸门 -> 晨报
晨报 -> 晨会验收
晨会验收 --> 回信清单: 对外来源
晨会验收 -> 教训沉淀: 有可复用结论
教训沉淀 -> 教训索引
教训索引 --> spec 正文
spec 正文 --> 逐包执行: 同路径自动注入
晨会验收 -> 每周防腐
每周防腐 --> 规范条目: 重复即沉淀
规范条目 --> spec 正文

晨会验收 --> 白天 原型与需求: 打回重签
```

## I 新增 G8 沉淀门 {span=2}

```limits
重复出现 2 次 | 2 | 3
```

判定规则：同一类问题在近 90 天出现第二次，G7 验收不通过。必须写一条规范才算完。

落点两处：流程层写 DECISIONS.md 一行，代码层写 .trellis/spec 一条。规范条目会随路径注入，第二次犯同样的错时 agent 当场看见。

这条把"防止以后的 agent 犯同样错误"从愿望变成机械判定。

## J 两个正交状态，推出看板六列 {span=2}

| 列 | 进入条件 |
|---|---|
| 未就绪 | gateState 不为 clear，按门分组 |
| 今晚队列 | 门已清零，且 runState 为 idle 或 queued |
| 执行中 | runState 为 running |
| 待验收 | runState 为 green 或 committed |
| 待发池 | runState 为 accepted |
| 停泊横幅 | runState 为 parked，不进列 |

gateState 由凭据与 hash 实时推导。runState 由事件流折叠重建。两者相乘得到列。新增一道门只改一个函数。

## K 验证优先的证据阶梯 {span=2}

| 级 | 证据 | 最低适用于 |
|---|---|---|
| L0 | 肉眼说好了 | 不接受 |
| L1 | 单测红绿 | 后端与契约 |
| L2 | 真机 harness 计数 | 新功能 |
| L3 | L2 加 stash 对照 | Bug 修复 |
| L4 | L3 加像素或几何测值 | 样式缺陷 |
| L5 | rubric 逐条签字 | 样式重设计 |

对外来的 PR 多一条硬规矩：必须用本仓 harness 跑，不用对方自带的测试。

## N 教训沉淀环境：三档 {span=2}

| 档 | 写在哪 | 谁看到 | 机制 |
|---|---|---|---|
| 局部 | 工作项的「记录」段 | 接手这个包的人 | 打开即见 |
| 复用 | `.trellis/spec/**` + `paths:` 前缀 | 碰到同路径文件的 agent | **自动注入** |
| 流程 | `DECISIONS.md` + RUNBOOK | 所有人每天 | 开工必读 |

索引（`LESSONS.md`）与正文（spec）分家：索引可审计、正文可注入。`lesson add` 硬校验 spec 有 `paths:`——不会被注入的教训等于没写。

90 天零引用的条目进 `lesson stale`。教训也会过期。

## O 自升级 {span=2}

```flow LR
(VERSION) -> doctor: 读版本
doctor -> {有待迁移?}
{有待迁移?} -> upgrade: 是
upgrade -> 备份
备份 -> 迁移脚本
迁移脚本 -> 写 VERSION
{有待迁移?} --> 一致: 否
写 VERSION -> 一致
```

三个件：`VERSION`（整数版本）、`migrations/<n>-<slug>.mjs`（必须幂等）、`.backup/<ts>/`（升级前自动备份）。

护栏：迁移本身是 `arch` 类工作项，要走 G1→G6；`doctor` 进 `npm run verify:loop`，schema 与实际文件不一致就红。
