## tl;dr

Snorkeling currently inherits Wave Terminal's telemetry and diagnostics-ping code paths. The default configuration contains `"telemetry:enabled": true`, and the runtime still uses several upstream `WAVETERM_*` environment variables for compatibility.

The inherited telemetry code is designed to avoid collecting personal information (PII), keystrokes, file contents, AI prompts, IP addresses, hostnames, or commands. Events are associated with an anonymous, randomly generated _ClientId_ (UUID). You can opt out at any time.

Here's a quick summary of what the inherited telemetry system may collect when enabled:

- Basic app/system info: OS, architecture, app version, update settings
- Usage metrics: app start/shutdown, active minutes, foreground time, tab/block counts and usage
- Feature interactions: tab creation, command actions, settings changes, and similar events
- Display info: monitor resolution and display count
- Connection events: SSH/WSL connection attempts, without hostnames or IPs
- AI usage metadata: model/provider selection, token counts, request metrics, and latency, without prompts or responses
- Error reports: crash/panic events with minimal debugging info

## How to Disable Telemetry

Telemetry can be disabled by setting the `telemetry:enabled` key to `false` in Snorkeling's general configuration file. It can also be disabled with:

```bash
wsh setconfig telemetry:enabled=false
```

## Diagnostics Ping

Snorkeling currently keeps the inherited diagnostics ping path. The ping is separate from usage telemetry and is intended to estimate active installs and versions in use.

The ping includes only the app version, OS/CPU architecture, local date, anonymous client ID, and whether usage telemetry is enabled or disabled. It does not include commands, files, prompts, responses, hostnames, IP addresses, or telemetry events.

To disable the diagnostics ping, set the `WAVETERM_NOPING` environment variable before launching Snorkeling. The variable name is still inherited from upstream Wave.

## Sending Telemetry

Provided that telemetry is enabled, telemetry is sent shortly after Snorkeling is first launched and then again periodically. It can also be sent during shutdown. When telemetry is sent, events are marked as sent to prevent duplicate transmissions.

### Sending Once Telemetry is Enabled

As soon as telemetry is enabled, a telemetry update may be sent regardless of how long it has been since the last send. This does not reset the usual timer for telemetry sends.

### When Snorkeling is Closed

Provided that telemetry is enabled, it may be sent when Snorkeling is closed.

## Event Types and Properties

The complete source of truth is the current source code. Relevant implementation areas include `pkg/telemetry`, `pkg/wcloud`, `pkg/wcore`, and the `telemetry:enabled` default in `pkg/wconfig/defaultconfig/settings.json`.

## GDPR Opt-Out Compliance

When telemetry is disabled, the inherited code path may send a minimal opt-out record associated with the anonymous client ID, recording that telemetry was turned off and when it occurred. After that, no telemetry or usage data should be sent while telemetry remains disabled.

## Deleting Your Data

Snorkeling does not currently document a separate public data-deletion support channel. If this project publishes a Snorkeling-specific telemetry backend or support process, this page should be updated before claiming a deletion workflow.

## Privacy Policy

Snorkeling does not currently publish a separate privacy policy in this repository. Treat this page as implementation documentation rather than a legal privacy policy.
