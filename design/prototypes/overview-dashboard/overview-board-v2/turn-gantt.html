Overview · 时间线 G3：按对话轮拆分

每行 = 一个会话，条内按对话轮拆成四类段：空闲（轮与轮之间）、 思考（估算）、工具执行（精确）、回复生成，每轮末尾一个完成点。 段全部由 SQLite 索引里的消息时间戳算出，不需要新埋点。切到 30m 窗口看轮级细节； 切换「降采样」对比段数封顶前后的 DOM 压力（看顶部统计）。

圆角固定 4px
Agent 会话（按最后活动倒序）
空闲（轮间隔） 思考（估算，斜纹） 工具执行（精确） 回复生成 完成点（每轮） 合并段（降采样） 未知（降级行）

段公式（唯一事实源）

段计算精度
思考t(assistant+toolCall) − t(上一条消息)估算
工具t(toolResult) − t(assistant+toolCall)精确
回复t(末条 assistant 文本) − t(最后 toolResult)精确
空闲t(下轮 user) − t(本轮末条)精确
完成点t(本轮末条)精确

真机验证（2026-11-25，真实会话 192 条消息）：toolResult → assistant+toolCall 中位 9.5~12.4s（思考+决策）、assistant → toolResult 中位 0.5s（工具）、 assistant → user 中位 135s（空闲）。assistant→toolResult 中位只有 0.5s 证明 assistant 条目时间戳 = 生成完成/工具发起时刻，所以「上一条 → assistant+toolCall」 这段间隔就是模型侧（思考）耗时。

误差成分（思考段必须标"估算"）

  • 思考段混有 网络/API 延迟与正文生成（该 assistant 条目同时带 text 时无法剔除）。
  • 一个 assistant 条目带多个 toolCall（并行工具）时只算一次，不拆分。
  • 回复段同样是"模型侧耗时"（含思考），与思考同族配色，但没有斜纹标记。
  • 用户输入耗时不可见（发生在两条消息之间，归入空闲段）。

性能设计 硬约束

  • 后端一次扫描：SQLite 索引 WHERE timestamp >= windowStart 归并成纯数字段数组 [{kind, fromMs, toMs}] + 完成点数组，RPC 不传任何文本。
  • 批读：一次 ≤20 会话，每会话 ≤200 轮；只对可见行（≤40）取数。
  • 段数封顶：每行渲染段 ≤60（超限合并最窄相邻段）；完成点 >30 抽稀；段 CSS 最小宽 2px。
  • 渐进渲染：首帧画 G2.1 粗条，段数据到达原地换段，DOM 结构不变、无布局抖动。
  • 降级：索引 stale/缺失的会话（下方「旧会话」行）保留两段式，永不阻塞首屏。

视觉与交互约定

  • 条外框圆角 4px（固定）；内部段是铺排矩形、不各自圆角，段间 1px 缝——多段拼接不糊。
  • 思考段细斜纹 = "估算"；工具段琥珀 = "精确"；完成点 = 蓝色细竖刻度 + 圆点。
  • 条内不渲染文字，所有信息走 tooltip（避免窄段塞文字造成回流）。
  • 轮级细节需要 30m/1h 细窗口：2h 窗口里 10s 思考段只有 ~1.5px，这是物理上限不是 bug。
