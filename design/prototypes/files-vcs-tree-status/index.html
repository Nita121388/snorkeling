四方案权衡

A 圆点

  • 能标出哪个文件/目录变了
    （我上一版说"不能"是错的）
  • 改动最小
  • 只有两态，分不出 M/U/D
  • 干净也要绿点 → 满屏点

B 图标变色 不推荐

  • 与「文件类型色」语义打架
  • 高饱和小色块满屏 → 显脏
  • 偏离 VS Code 实际做法

C 结合

  • 信息最全
  • 双重编码，视觉最吵
  • 窄栏易挤

D 文字+字母 推荐

  • 不污染 icon 类型色
  • 文件行：字母 M/U/D 表类型
  • 文件夹行：数字表变更数
  • 干净时完全静默

为什么图标变色显「脏」

设计原理
  1. icon 颜色本来承载「文件类型」：文件夹黄、代码蓝、图片紫。按 VCS 状态换色后， 用户分不清「这是变色了的代码图标」还是「这文件本身是橙色类型」，两套编码抢同一个通道。
  2. 小面积高饱和色块堆叠：icon 是 13px 左右的实心块，几十行彩色叠加， 整棵树会花掉、失焦；文字是细笔画，同色率下温和得多。
  3. VS Code / JetBrains 实际做法：文件名文字变黄/绿，图标只加 M/U/D 角标，不整体换 icon 色。我上一版把这条说错了。
  4. 信息密度：文字着色 + 字母，一个通道承载「哪个变了」，另一个承载「怎么变的」， 而 icon 换色只能承载前者。

性能预算（硬约束）

不影响性能
RPC 调用次数（整个目录树）1 次 每行渲染计算O(1) 查表 status 聚合O(M) 一次 D 方案新增 DOM仅变更行 +1 span 滚动 / hover 新增请求0 目录切换 debounce250 ms
做法
  1. 一次 RPC 拿全：RemoteVcsRepositoriesCommand({ path, scandepth, statuslimit: 2000, includeparent: true })。绝不对每行单独请求
  2. 一趟遍历建两套索引：Map<目录首段, 变更数> + Map<相对路径, 变更码>，同趟 O(M)
  3. 行尾槽位固定：.trail 始终存在，方案切换只改内容不改布局 → 无 reflow
  4. 只算可见层级：只给当前展开层直接子行打标记
  5. 跳过噪音目录：node_modules / .git / dist / target
  6. 缓存 + 精准失效：directoryVcsStatusCache（key = conn + dir），仅 VCS 操作成功 / 手动刷新 / 目录变更时失效

语义色（跨 4 套主题）

修正
不要用 --accent-color：暗色绿 rgb(88,193,66)、浅色紫 #9e60c5、 极简黑 #1a1a1a、暖色橙 #c38057，「干净」语义会漂移。
用 --success-color（4 套均绿系）+ --warning-color（modified）+ --error-color（deleted）。
干净不要用绿（会与 untracked 的绿混淆）。干净 = 不变色， 由 Files Header 路径变色单独承担「一眼看出干净」。
