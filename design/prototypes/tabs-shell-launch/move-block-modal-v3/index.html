0 · 决定（本原型按「推荐列」绘制）

现状问题：「新建」和「选择」被拆成两条菜单，而弹窗自己不能新建 —— 菜单多不是原因，是结果。
决定推荐理由
菜单条数 4 条 → 1 条 Move to Tab… 选哪个 tab、要不要新建，本来就是同一个问题的两个答案，不该在菜单层先分叉。
Copy 的去留 保留，每行两个图标（→ Move / ⧉ Copy），不做模式切换 复制 agent 会话块到另一个 tab 是真实用法，但不值得再占一条菜单；做成模式状态反而多一步心理建模。
New tab 命名 不输名字，沿用源 tab 名 + 去重（My Tab → My Tab 1） 保持「一次点击完成」。重命名走已有的 tab 重命名，不在这里加第二个输入口。

4 · 为什么现在「像只支持 agent Block」

代码层并不是按 block 类型拦的：makeBlockMoveMenuItems 对任何 !preview && !ephemeral 的 block 都产出条目。 真正的原因是入口依赖各 view 主动接力，谁的右键菜单不吃这一口，谁就「没有 Move」。
入口现状说明
Block header ⋯ 菜单全 block保底路径。任何非 preview / 非 ephemeral block 都有 → 新方案以它为主路径
Block 框右键（header / 空白区）全 blockshowBlockContextMenu，但会在 .block-content 内提前 return
view/term有appendBlockMoveMenuItems —— agent / 普通终端都走这条，所以「看起来只有 agent」
view/vcs有commit / 文件列表右键
view/preview-directory有Files 目录树 / 表格
view/preview-explorer有Files 树
view/processviewer有进程列表
view/preview-model缺markdown / 图片 / webview 预览块的右键菜单没接 → 这里右键**看不到 Move**
view/aisessions缺会话列表自己的菜单
view/codeeditor / tsunami / …缺未接 useBlockMoveMenuItems
落地口径：⋯ 菜单做保底（已成立，不改），缺的 4 个 view 逐个补 appendBlockMoveMenuItems， 并加一条守卫单测，防止以后有人把「新建」又拆回菜单。
